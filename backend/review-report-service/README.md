# Daily store projection (INT-45)

The application defaults to **`REPORT_REVENUE_EVENT=order.completed`**, supplied through Config Server, following the documented completed-order revenue policy. Revenue is the completed order's final amount, in Vietnam business time, before refunds. Cash and declared transfer are separate from confirmed bank receipts. `false` remains an explicit operational pause; do not change recognition policy against existing projection trackers.

The local activation on 13 November 2026 started from zero daily-stat rows and zero order trackers. Kafka replays retained events using the existing idempotent projection; it does not fabricate missing historical events or delete manual data. Other deployments must inspect their baseline and retained event window before activation. Dashboard's orders-placed-today KPI comes directly from Order Service, not the completed-order revenue count.

The supported policies are `order.completed` or `payment.confirmed`. The selected event alone supplies revenue and business date; arrival order never selects a policy. Order mode reads numeric `totalAmount`, `paymentMethod`, and `completedAt` (otherwise envelope `occurredAt`). Payment mode reads numeric `amount`, `method`, and `paidAt` (otherwise `occurredAt`). Accepted methods are `COD`, `BANK_TRANSFER`, `CASH`, `MIXED` and `UNVERIFIED`; dates use Asia/Ho_Chi_Minh. Collection events carry explicit cash and declared transfer amounts. These are event amounts, not a newly inferred gross/net calculation. Producer source must match the topic. Missing money/method/time, invalid IDs, inconsistent stores and changed authoritative facts fail without acknowledgment.

Both topics can provide `storeId`. Until the selected event and a positive store ID exist, a tracker remains pending (`store_id=0` is internal only, never a daily-stat row). The companion event only enriches store/observed flags; it cannot override money/date/method. Event claims, locked order trackers and atomic daily-stat increments commit together. Retries after a rollback remain eligible. A second event ID for an already contributed order cannot add revenue again.

`order.cancelled` is recorded for reconciliation but makes **no refund delta**. Refunds, changed authoritative amounts, policy changes and historical/backfill corrections require a separately approved migration/reconciliation plan; do not switch policy against existing trackers or delete production stats. Existing seed/manual stats are not automatically reconciled. Before activation, establish the projection baseline and replay window, confirm producer contracts, retention and durable DLQ handling. The existing error handler deliberately does not acknowledge failed recovery without a durable DLQ.

Local verification covers actual PostgreSQL migrations, transactions, concurrent delivery, rollback/retry and reordered event fixtures. It is not evidence of live Kafka/producer integration or an approved revenue policy. Run `:review-report-service:test` normally; set `CLUCKY_TEST_DB_URL` and `CLUCKY_TEST_DB_PASSWORD` for the optional isolated PostgreSQL suite (user `postgres`, schema `review_report_service`).
