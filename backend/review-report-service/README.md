# Daily store projection (INT-45)

The Kafka projection is **disabled by default** (`REPORT_REVENUE_EVENT=false`, supplied through Config Server). INT-45 requires Report + Payment/Order approval of recognition time, gross/net/refund treatment and ordering before production activation. This PR does not approve that policy or certify INT-45 complete.

After that approval, the supported policies are `order.completed` or `payment.confirmed`. The selected event alone supplies revenue and business date; arrival order never selects a policy. Order mode reads numeric `totalAmount`, `paymentMethod`, and `completedAt` (otherwise envelope `occurredAt`). Payment mode reads numeric `amount`, `method`, and `paidAt` (otherwise `occurredAt`). Accepted methods are `COD` and `BANK_TRANSFER`; dates use Asia/Ho_Chi_Minh. These are event amounts, not a newly inferred gross/net calculation. Producer source must match the topic. Missing money/method/time, invalid IDs, inconsistent stores and changed authoritative facts fail without acknowledgment.

Both topics can provide `storeId`. Until the selected event and a positive store ID exist, a tracker remains pending (`store_id=0` is internal only, never a daily-stat row). The companion event only enriches store/observed flags; it cannot override money/date/method. Event claims, locked order trackers and atomic daily-stat increments commit together. Retries after a rollback remain eligible. A second event ID for an already contributed order cannot add revenue again.

`order.cancelled` is recorded for reconciliation but makes **no refund delta**. Refunds, changed authoritative amounts, policy changes and historical/backfill corrections require a separately approved migration/reconciliation plan; do not switch policy against existing trackers or delete production stats. Existing seed/manual stats are not automatically reconciled. Before activation, establish the projection baseline and replay window, confirm producer contracts, retention and durable DLQ handling. The existing error handler deliberately does not acknowledge failed recovery without a durable DLQ.

Local verification covers actual PostgreSQL migrations, transactions, concurrent delivery, rollback/retry and reordered event fixtures. It is not evidence of live Kafka/producer integration or an approved revenue policy. Run `:review-report-service:test` normally; set `CLUCKY_TEST_DB_URL` and `CLUCKY_TEST_DB_PASSWORD` for the optional isolated PostgreSQL suite (user `postgres`, schema `review_report_service`).
