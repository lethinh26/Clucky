## BE-03 — Ánh xạ entity và repository Order để lưu đơn hàng, chi tiết hóa đơn, lịch sử trạng thái và yêu cầu đặt tiệc

**Phụ trách:** Trần Đức Anh · **Sprint:** 1 · **Ước lượng:** 3 SP
**Phụ thuộc:** UI-03, UI-06

### 1. User Story

- **Là người phát triển**, tôi muốn ánh xạ entity và repository Order để lưu đơn hàng, chi tiết hóa đơn, lịch sử trạng thái và yêu cầu đặt tiệc.

### 2. Công việc

- Lập bảng đối chiếu ngay trong phần bàn giao: bảng/cột SQL → field Java → kiểu/nullability/constraint → khớp hoặc chênh lệch. Đọc V2 và entity trước, chưa sửa DB.
- Làm orders trước, rồi items/history/refund; party_orders độc lập về FK. Đối chiếu JSONB bằng object có cả chuỗi/số/mảng, không serialize thành chuỗi JSON hai lần. Tách rõ lỗi mapping hiện có với thay đổi schema bổ sung version cần duyệt.
- BIGINT/BIGSERIAL dùng Long; NUMERIC dùng BigDecimal đúng precision/scale; TIMESTAMPTZ dùng Instant như code hiện có; DATE dùng LocalDate, TIME dùng LocalTime. Cột nullable cần kiểu cho phép null. Không dùng float/double cho tiền.
- So default SQL với giá trị khởi tạo Java: DB default không tự áp dụng khi ORM gửi null tường minh. Kiểm tra trường bắt buộc được gán từ đâu; không tùy tiện thêm callback hoặc đổi luật nghiệp vụ.
- Chỉ sửa mapping bị lệch. Giữ FK trong schema đang sở hữu; ID thuộc service khác không thành JPA association/FK xuyên schema. HTTP trả DTO, không expose entity.
- Nếu cần đổi bảng/index: ghi chênh lệch, lý do, ảnh hưởng dữ liệu cũ và migration mới để duyệt. Không sửa V1/V2 đã áp dụng, không dùng ddl-auto=update/create, không bật baseline tự động để bỏ qua DB có dữ liệu.

**Không bao gồm:** endpoint nghiệp vụ, seed tài khoản/credential thật, truy cập database service khác, mở rộng tích hợp ngoài phạm vi. Tiền/ID/thời điểm ở các ví dụ là fixture, không phải dữ liệu sản xuất.

### 3. Contract và đầu ra

| Bảng → entity có sẵn | Cột/ràng buộc cần chú ý |
| --- | --- |
| `orders` → `Order` | order_code unique; customer_id/store_id là ID bên ngoài; type DELIVERY/PICKUP; tiền NUMERIC(12,0), điểm INT; receiver/scheduled_at có thể null theo SQL |
| `order_items` → `OrderItem` | FK order_id nội bộ; giữ item_name/unit_price/line_total và JSONB options_snapshot/toppings_snapshot; product_id/combo_id chỉ là ID; quantity > 0 |
| `order_status_history` → `OrderStatusHistory` | FK order nội bộ; from_status/changed_by/reason nullable theo SQL; to_status bắt buộc; không thay lịch sử cũ bằng trạng thái hiện tại |
| `refund_requests` → `RefundRequest` | amount, reason, status; reviewed_by/reviewed_at nullable; customer_id không liên kết entity User ở service khác |
| `party_orders` → `PartyOrder` | expected_date là DATE; đủ contact/phone/guest_count/content; customer/store là ID, không tạo FK xuyên service |

### 4. Tiêu chí hoàn thành

- Đối chiếu tất cả bảng/cột với entity, migration và config: Có ma trận đầy đủ; schema đúng `order_service`, kiểu/nullability/constraint/index không bị bỏ sót; chênh lệch có quyết định xử lý
- Tạo order mã `MAP-ORDER-01`, item giá 45000/số lượng 2 và JSON snapshot, history, refund; thêm party order: Lưu/đọc đủ 5 bảng, JSON giữ cấu trúc và tiền giữ đúng giá trị; không truy cập Catalog/Identity
- Đọc lại đơn đã lưu khi dữ liệu món ở nguồn thay đổi: item_name/unit_price/options/toppings vẫn là snapshot đã lưu, không lấy giá/tên mới để ghi đè hóa đơn
- Ghi order_code trùng hoặc item quantity=0; tìm order bằng customer/store khác: DB từ chối dữ liệu vi phạm; scoped repository không trả đơn của người/quán khác
- Sau khi chốt migration version: hai transaction đọc cùng phiên bản rồi cùng cập nhật: Cập nhật sau bị phát hiện xung đột, không ghi đè im lặng. Nếu chưa chốt/triển khai thì ghi BLOCKED, không đánh PASS toàn task
- Trên DB kiểm tra riêng: áp dụng migration, lưu dữ liệu mẫu, khởi động lại; đối chiếu history và dữ liệu: Migration versioned cũ không chạy lại, checksum không bị sửa, dữ liệu không mất; Hibernate validate chứ không tự sửa schema. DB cũ không có history chỉ xử lý sau khi chốt mục 5
- Bàn giao contract, mã lỗi và kết quả tự kiểm thử kèm commit, môi trường, bằng chứng; ghi rõ lỗi hoặc phần còn bị chặn.

### 5. Điểm cần chốt

- DB đích đã có bảng và flyway_schema_history chưa?: PIC task nhận thông tin từ UI-03/UI-06: database/schema, profile Config Server, lịch sử version và chênh lệch với SQL trong repo. Database phải tồn tại trước khi Flyway tạo schema. Chưa rõ baseline thì dừng phần migration trên DB đó, vẫn đối chiếu source được.
- Version/optimistic locking trong AC cũ nhưng chưa có cột: Trần Đức Anh chốt với owner Order cơ chế concurrency và migration bổ sung, dữ liệu backfill, giá trị khởi tạo. Không bỏ yêu cầu cũ hoặc đánh PASS, không tự sửa V2. Chặn phần nghiệm thu optimistic locking; không chặn mapping các cột đã có.
