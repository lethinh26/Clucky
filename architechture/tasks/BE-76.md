## 1. Làm xong task này thì dùng được gì?

Customer đăng nhập Google qua Firebase, backend Identity xác minh ID token rồi phát JWT/refresh theo hệ thống Clucky. Tài khoản mới phải hoàn tất password trước khi tạo CUSTOMER ACTIVE; PostgreSQL vẫn là nguồn user/role/status, không dùng Firebase token thay access JWT.

Giữ contract đã duyệt: user đã link hoặc email cũ đủ điều kiện → JWT; user mới → REQUIRES_PASSWORD + pendingToken TTL 10 phút dùng một lần. Nhận DEP-23 về Firebase config/runbook, không Google login cho Staff/Admin hoặc làm E2E UI INT-74 trong task này.

## 3. API và trust contract

| API / trường hợp | Xử lý cần bàn giao |
|---|---|
| POST /api/auth/google {idToken} | Server verify chữ ký/aud/iss/exp và email_verified, project/provider Google đúng; không chỉ decode JWT |
| firebase_uid đã link | Tìm user PostgreSQL, kiểm active/locked/role; phát session theo BE-17, không trust role từ Firebase/client |
| Email đã tồn tại nhưng chưa link | Theo contract link bằng verified email, kiểm normalization/uid conflict và eligibility; không liên kết vào Staff/Admin hoặc bỏ khóa tài khoản |
| User mới | Pending challenge opaque, dữ liệu uid/email/name/avatar trusted phía server; response REQUIRES_PASSWORD và pendingToken, chưa access session |
| POST /api/auth/google/complete {pendingToken,password} | Validate password, challenge còn hạn/chưa dùng; BCrypt tạo CUSTOMER ACTIVE, bỏ OTP vì Google email đã verify; trả session chuẩn |
| Register email đã tồn tại | 409 EMAIL_EXISTS kể cả tài khoản Google; xử lý race bằng DB uniqueness, không chỉ exists-check |

Pending token là credential ngắn hạn, không log/query URL hoặc dùng như access token. Không nhận email/uid/role/storeId/active do browser khai lại ở complete. Google avatar URL không mặc định là Cloudinary publicId để destroy; không fetch remote URL tùy ý.

## 4. Thứ tự triển khai cụ thể

1. Cùng owner BE-17/Identity thống nhất JWT/refresh cookie, password policy và link-existing rules; dùng AuthService/session implementation hiện có. Chốt rõ existing email chưa verified, uid đã link khác và privileged/locked accounts, không tự bypass để “Google login thành công”.
2. Đối chiếu schema thật, thêm migration mới cho firebase_uid unique nullable và nullable password_hash theo contract đã duyệt nếu cần; phone đã nullable không làm lại. Không sửa V1/V2 đã áp dụng, không tự tạo user password null trước complete trái flow.
3. Cấu hình Firebase Admin server bằng credential runtime/secret store và project đúng, verify token bằng SDK phù hợp phiên bản. Ghi runbook DEP-23 cho Google provider/authorized domains/client config/server credential; không commit service-account JSON/private key.
4. Implement /google: verify trước DB mutation, kiểm Google provider/project/email, lookup uid/email, enforce role/status. Link có transaction/constraint để hai uid không chiếm cùng account; không update role/password của user cũ từ payload Firebase.
5. User mới: lưu pending context và TTL10m theo config/contract, token có entropy đủ và không chứa trust data client có thể sửa. Không persist password plaintext hoặc phát access/refresh trước complete.
6. Complete: validate password trước consume, dùng GETDEL nguyên tử và unique constraint chống cạnh tranh Redis/Postgres. Policy 05/11: consume một lần, DB failure cần bắt đầu Google lại; DB commit nhưng mất response thì Google login vào user đã có. Không GET rồi DEL riêng hoặc ghi đè mật khẩu user thắng cuộc đua.
7. Persist user/uid/hash trước phát session; unique email/uid conflict thành lỗi catalog an toàn. DB commit nhưng response/cookie thất bại phải có đường đăng nhập/retry rõ, không sinh account trùng hoặc trả password/ID token trong lỗi.
8. Bàn giao INT-74 response states/cookie/CORS/CSRF theo auth hiện hành và fixtures verified/unverified/expired/wrong-project. E2E Firebase thật cần project/consent owner, không tự mở browser/đăng nhập tài khoản trong lượt viết detail.
