## 1. Mục tiêu nghiệp vụ

Customer đăng nhập Google qua Firebase nhưng JWT và user source of truth vẫn do Identity quản lý.

## 2. Phạm vi

### Bao gồm

- POST auth/google và google/complete, user link/create an toàn, JWT hoặc REQUIRES_PASSWORD.
- Giữ migration bổ sung firebase_uid unique nullable và thay đổi nullable có căn cứ; không viết lại V1.
- Firebase Admin verify chữ ký/aud/iss/email_verified; PostgreSQL là user source of truth.
- POST /auth/google: user cũ/link email → JWT; user mới → REQUIRES_PASSWORD + pendingToken.
- POST /auth/google/complete: password BCrypt, pendingToken TTL 10 phút/một lần; email trùng register → 409 EMAIL_EXISTS.
- Gộp DEP-23: cấu hình Firebase project/provider/env và runbook; không commit service account secret.

### Không bao gồm

Không Google login cho Admin/Staff, không rewrite V1; UI E2E ở INT-74.

### Luồng Google giữ từ đặc tả

- Đối chiếu SRS/API/database docs.
- Migration mới (không sửa Flyway V1): `users` thêm `firebase_uid` unique nullable; `password_hash` + `phone` chuyển nullable.
- Firebase Admin SDK verify ID token: chữ ký + `aud` + `iss` + `email_verified`. Không dùng Firebase làm user store — PostgreSQL là source of truth.
- `POST /api/auth/google` {idToken}:
  - `firebase_uid` đã link → trả JWT.
  - Email đã tồn tại nhưng chưa link → link `firebase_uid`, trả JWT.
  - Chưa có user → tạo `pendingToken` (Redis TTL 10 phút, chứa uid+email+name+avatar) → trả `{status: "REQUIRES_PASSWORD", pendingToken}`.
- `POST /api/auth/google/complete` {pendingToken, password} → tạo CUSTOMER ACTIVE (bỏ OTP vì Google đã verify email), hash BCrypt → trả JWT.
- `POST /api/auth/register` với email đã tồn tại (kể cả tài khoản Google) → `EMAIL_EXISTS` 409.
- Giữ Config Server, Eureka, Gateway, database/schema riêng, RBAC/storeId.
- Mail Sender nằm trong Notification Service, Gmail SMTP App Password từ env/Config Server.
- Cloudinary là external media provider; không lưu binary trong PostgreSQL, không lộ `CLOUDINARY_API_SECRET`.
