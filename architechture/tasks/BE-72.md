## 1. Làm xong task này thì dùng được gì?

Admin thay ảnh product/combo qua API, lưu URL/publicId vào đúng resource và đọc lại được sau reload. Lỗi upload/commit không phá ảnh đang dùng; UI nhận đúng response/error để hiển thị, không chỉ đổi blob URL local.

Tiếp tục endpoint đã có, không tạo controller/adapter thứ hai. BE-70 chịu adapter/tích hợp provider, BE-71 validation, BE-74 cleanup; không nhận scope banner/avatar hoặc form UI.

## 3. Route và mutation contract

| API | Input / quyền | Output |
|---|---|---|
| POST /api/catalog/products/{id}/image | ADMIN, productId dương/tồn tại, multipart file theo BE-71 | Resource/media response đã chốt, metadata đã lưu của đúng product |
| POST /api/catalog/combos/{id}/image | ADMIN, comboId dương/tồn tại, multipart file | Tương tự combo, không nhầm primary key product cùng số |

Metadata từ provider/server, không nhận URL/publicId client để gán tài nguyên người khác. Response không bao gồm API secret/raw provider map. oldPublicId null của ảnh legacy không phải lỗi phải xóa bằng URL; không suy publicId từ URL.

Thành công endpoint là metadata commit theo contract, không mặc định cleanup asset cũ đã hoàn tất. Replay/replace concurrent cần operation/version policy, không để request cũ ghi đè ảnh mới rồi cleanup nhầm ảnh đang dùng.

## 4. Thứ tự hoàn thiện

1. Cùng BE-70/71/75 và owner tích hợp chốt request/response/null/error, dùng handler hiện có. Phân biệt resource imageUrl/imagePublicId với adapter secureUrl/publicId; không yêu cầu frontend đoán field.
2. Validate actor/id/resource/file trước provider call; lỗi không tồn tại/forbidden phải không tạo asset. Giữ Admin-only, không mở cho Manager vì menu quản trị có nút.
3. Gọi một adapter BE-70, kiểm result rồi cập nhật metadata đúng record trong transaction. Không trả HTTP success trước commit, không gán null result hoặc dùng URL fake khi provider disabled.
4. Chốt lost-update policy cho hai upload đồng thời, version/conditional save hoặc phương án tương đương; losing attempt tạo orphan phải được giao BE-74, không xóa ảnh hiện tại.
5. DB failure sau upload: giữ metadata/ảnh cũ và durable orphan handoff. Commit thành công: cleanup cũ sau commit theo BE-74; không chỉ afterCommit callback rồi coi crash recovery đã đủ.
6. Đọc lại resource/menu và cache invalidation theo BE-54 sau commit. Không để cache chứa metadata chưa commit hoặc nhầm ảnh combo/product; chốt trạng thái response nếu cleanup còn pending.
7. Bàn giao API samples cho INT-72 và consumer đã ghi trong dependency. Nếu task cũ nhắc INT-73, xác nhận phần nối thực tế với owner, không tự sửa edge/lịch hoặc nhận banner/avatar.

## 7. Tiêu chí nghiệm thu cụ thể

Chưa chạy các ca này. P1 đang ảnh A; combo C1 có ID số giống một product để bắt nhầm resource.

| AC | Thao tác | Kết quả cần quan sát |
|---|---|---|
| AC-01 | Upload B cho P1/C1, GET lại resource/menu | URL/publicId đúng record, response mapping đúng, ảnh không chỉ local preview |
| AC-02 | Role sai, id âm/không tồn tại, multipart thiếu file | Lỗi chuẩn, không provider call/metadata mutation ngoài quyền |
| AC-03 | Provider thiếu URL/ID, timeout hoặc disabled | Không lưu null/success giả; A vẫn dùng được |
| AC-04 | Upload B xong nhưng DB commit lỗi | DB vẫn A, không delete A; B có đường orphan recovery |
| AC-05 | Hai replace cùng resource/retry request cũ | Kết quả theo version/identity policy; cleanup không xóa ảnh cuối còn tham chiếu |
| AC-06 | Cleanup A lỗi sau commit B; resource cũ chưa có publicId | B vẫn hoạt động, pending cleanup được theo dõi; legacy URL không dùng để destroy tùy ý |
