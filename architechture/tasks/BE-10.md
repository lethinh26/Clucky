## BE-10 — Chuẩn hóa response, phân trang và xử lý exception để các API trả mã lỗi thống nhất, không lộ lỗi nội bộ

**Phụ trách:** Lê Phú Thịnh · **Sprint:** 1 · **Ước lượng:** 3 SP
**Phụ thuộc:** UI-03

### 1. User Story

- **Là người phát triển**, tôi muốn chuẩn hóa response, phân trang và xử lý exception để các API trả mã lỗi thống nhất, không lộ lỗi nội bộ.

### 2. Công việc

- Lập ma trận nơi tạo lỗi: advice của business service/Audit, security handler, Gateway reactive handler; ghi lớp đã có và điểm chưa cùng contract. Không scaffold lại các file đã có.
- Đối chiếu mã đang được caller sử dụng với catalog. Chỉ thêm/sửa code khi thật sự thiếu: tên ổn định, status đúng, đủ vi/en; mỗi status có một defaultForStatus, mã nghiệp vụ cùng status không tự nhận default.
- Khi triển khai có thay catalog, dùng `node scripts/generate-errors.mjs` tại gốc repo để sinh lại; bàn giao cùng các output. Lệnh này là hướng dẫn cho người triển khai, chưa chạy khi biên soạn detail.
- Sửa ApiError/ApiException/advice ở đúng nơi cần thiết; backend lấy message từ generated enum. Không sửa tay ErrorCode.java, error-codes.generated.ts hoặc errors.generated.json.
- Đối chiếu entry point/access denied của servlet và Gateway; ControllerAdvice không thay thế security handler. Gateway không ghi lại body khi response đã committed, không nuốt lỗi rồi trả 200.
- Đối chiếu PageResponse và các caller hiện có; giữ content DTO, index trang và tổng số phần tử. Chỉ sửa chênh lệch trong phạm vi contract được duyệt.
- Đối chiếu resolver lỗi của cả Next.js và React; known code → locale tương ứng; unknown code → status mặc định → INTERNAL_ERROR. Đổi ngôn ngữ phải dịch lại lỗi, không hiển thị raw message do server trả.
- Người phụ trách chạy kiểm tra được phép theo contract và lưu bằng chứng; nếu đang sửa task detail thì không chạy generator, test, lint, typecheck hoặc build.

**Không bao gồm:** dịch dữ liệu người dùng, viết lại UI của mọi màn, sửa generated thủ công, thêm network Error Service, thêm dependency chỉ để bọc 6 trường lỗi, đổi toàn bộ success response ngoài phạm vi.

### 3. API

| Trường | Kiểu/ý nghĩa |  |
| --- | --- | --- |
| timestamp | Chuỗi thời điểm ISO-8601 từ Instant, không phải chuỗi giờ local thiếu offset |  |
| status | HTTP status dạng số, khớp status của response và catalog |  |
| error | Reason phrase theo status; không dùng để frontend phân nhánh |  |
| code | Mã ổn định từ contracts/errors.json, ví dụ VALIDATION_ERROR hoặc RESOURCE_CONFLICT |  |
| message | Thông báo tiếng Anh an toàn trong catalog, không lấy Throwable.message |  |
| path | Đường dẫn request; không đưa query chứa token/credential vào body lỗi |  |
| Đầu vào/nguồn lỗi | Status/code mặc định | Yêu cầu |
| DTO validation, JSON hỏng, kiểu tham số sai | 400 / VALIDATION_ERROR | Không trả rejectedValue chứa mật khẩu hoặc raw parser message |
| Chưa xác thực/token sai | 401 / UNAUTHENTICATED | Security layer cũng dùng ApiError; giữ WWW-Authenticate: Bearer |
| Token đúng nhưng thiếu quyền | 403 / FORBIDDEN | Không mô tả dữ liệu bị cấm trong message |
| Resource không tồn tại | 404 / RESOURCE_NOT_FOUND | Không để not-found rơi thành 500 |
| Unique constraint hoặc optimistic lock conflict | 409 / RESOURCE_CONFLICT | Không lộ SQL/constraint detail; mã domain cụ thể chỉ dùng khi có trong catalog |
| Lỗi không dự kiến | 500 / INTERNAL_ERROR | Thông báo chung an toàn, không trả exception/stack trace |

### 4. Tiêu chí hoàn thành

- Gây validation, unauthenticated, forbidden, not-found, conflict và unexpected trên môi trường kiểm tra: Mỗi response có đủ 6 trường đúng kiểu; status/code khớp bảng mục 3; không rơi về HTML hoặc 200
- Sau thay đổi catalog đã duyệt, sinh output và người phụ trách chạy `node scripts/generate-errors.mjs --check`: Không drift; 10 module Java và hai frontend có cùng danh mục/status; vi/en đầy đủ, generated không sửa tay
- Exception giả chứa SQL/password marker; body JSON hỏng chứa giá trị nhạy cảm giả: Response chỉ có message catalog, không có raw exception, SQL, stack trace hoặc rejectedValue nhạy cảm
- Token lỗi ở Gateway và khi gọi service trực tiếp: Đều trả 401/UNAUTHENTICATED theo contract, không chỉ advice của controller đúng
- Lỗi nghiệp vụ dùng ApiException với code có sẵn: Giữ đúng code/status/message của domain, không bị đổi thành INTERNAL_ERROR hoặc lỗi generic không cần thiết
- Cả hai frontend nhận code lạ/status 409/message nguy hiểm giả; tiếp theo code/status đều không biết: Lần đầu hiển thị RESOURCE_CONFLICT theo locale; lần sau INTERNAL_ERROR; không hiện raw message
- Nhận known code rồi đổi vi/en: Giữ code/logic, thông báo đổi theo locale; không dùng bản dịch làm khóa nghiệp vụ
- Trả page rỗng rồi page có DTO; kiểm tra default size/max và invalid input theo quyết định mục 5: Content/tổng/trang đúng, không serialize entity; page rỗng không 404; invalid input đúng quy tắc đã ghi, chưa chốt thì chưa PASS phần này
- Gateway gặp lỗi khi response đã committed; method không hỗ trợ gây 405: Không ghi JSON lỗi lần hai vào response đã gửi; 405 không bị đổi thành 500
- Bàn giao contract, mã lỗi và kết quả tự kiểm thử kèm commit, môi trường, bằng chứng; ghi rõ lỗi hoặc phần còn bị chặn.

### 5. Điểm cần chốt

- Khi thêm mã domain, status/message nào là đúng?: Lê Phú Thịnh phối hợp owner domain trước khi thêm catalog; không thay nghĩa code cũ đang được frontend dùng. Chặn mã mới chưa thống nhất, không chặn sửa generic handler.
- page/size âm và sort lạ trả lỗi hay được chuẩn hóa?: Owner API và BE-10 chốt theo contract endpoint; config hiện có default/max không tự mô tả đầy đủ hành vi invalid input. Ghi trường hợp cụ thể và kết quả, không tự sửa global resolver để hợp thức hóa giả định.
- Endpoint đã có success envelope khác PageResponse xử lý thế nào?: Liệt kê caller bị ảnh hưởng và chốt với owner FE/API; không đổi hàng loạt ngoài task hoặc kết luận sample record là contract của mọi endpoint.
