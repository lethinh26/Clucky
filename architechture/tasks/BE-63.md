## BE-63 — Vận hành email: ghi nhận failure/DLQ bền vững, truy vết các lần gửi và cung cấp API tra cứu log đúng quyền

**Phụ trách:** Mai Sơn Việt · **Sprint:** 3 · **Ước lượng:** 5 SP
**Phụ thuộc:** BE-62, BE-09, KAFKA-01, BE-15

### 1. User Story

**Tiến độ 11/11/2026: đã triển khai, chờ nghiệm thu.** Failure outbox/publisher, metrics, API filter/detail và Manager scope. Retry thủ công có contract riêng hỗ trợ UI-50, không thay đổi ranh giới retry tự động. [Contract và checklist chưa chạy](../docs/Email_Operations_2026-11-11.md).

- **Là người phát triển**, tôi muốn vận hành email: ghi nhận failure/DLQ bền vững, truy vết các lần gửi và cung cấp API tra cứu log đúng quyền để triển khai và tích hợp đúng dữ liệu, quyền và contract của hệ thống.

### 2. Công việc

- Nhận BE-67/78: failure event/DLQ durable, trace/metrics/runbook và read email-log API
- Filter recipient/status/template/date, pagination/count theo quyền
- Không UI-50 retry thủ công/backlog, không alerting stack mới hoặc gửi mail báo lỗi mail
- Chốt log scope và field allowlist với BE-62/RBAC
- Nối terminal failure→durable intent→DLQ/replay theo KAFKA-08
- Triển khai scoped query/filter và trace/metrics, clean async context
- Viết runbook success/failure/unknown và kiểm API/DLQ outage

### 3. API

| API | Quyền / yêu cầu |
| --- | --- |
| `GET /api/notifications/email-logs` | ADM/MGR theo API; scope store phải trusted, auth/OTP/global log không tự gán quán từ email |

- Failure identity có delivery/source event/correlation/attempt/time/category; ACK sau durable boundary đã chốt
- Metrics labels cardinality thấp, không recipient/eventId làm label; log/API/DTO bỏ body/OTP/credential
- SENT/accepted khác inbox delivered, retry thuộc BE-62

### 4. Tiêu chí hoàn thành

- Admin lọc log theo recipient/status/template/kỳ: Kết quả/page/total đúng fixture
- Manager quán A đổi store/filter hoặc đọc log OTP không scope: Không lộ ngoài scope, không fallback toàn hệ thống
- Customer/Staff gọi email-log API: Deny, không lộ recipient/count
- Input query/date/page invalid: Lỗi catalog sạch, không query rộng vô hạn
- Delivery hết retry/permanent failure: Một terminal intent bền vững, trace đủ message/event/attempt
- DLQ/broker lỗi trước publish/ACK: Không ack mất failure; có retry/recovery
- Replay terminal message hoặc restart publisher: Không nhân failure effect/mất identity
- Subject/error/exception chứa canary OTP/password: API/log/DLQ không lộ marker, vẫn debug được category/IDs
- Hai async email xử lý đồng thời: Correlation context không lẫn giữa messages và được dọn
- Metrics nhiều recipient/event: Label không tăng cardinality theo từng người/event
- SMTP accepted/unknown/failure trong log: Phân biệt outcome, không tuyên bố đã inbox
- API/detail thao tác retry chưa được duyệt: Không thêm mutation endpoint hoặc mở quyền để chiều UI hoãn
- Bàn giao contract, mã lỗi và kết quả tự kiểm thử kèm commit, môi trường, bằng chứng; ghi rõ lỗi hoặc phần còn bị chặn.

### 5. Điểm cần chốt

- Owner Notification/RBAC chốt Manager được xem nhóm log nào, mask recipient/subject/lastError
- Chốt filter exact/partial/timezone/date field/range và retention
- Chốt terminal failure key/replay ownership, topic policy từ KAFKA-08; chưa chốt không ack bỏ event
