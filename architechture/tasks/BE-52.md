## BE-52 — Định nghĩa DTO và khung API thông báo, thống nhất phân trang, trạng thái đã đọc và đích điều hướng cho hai ứng dụng

**Phụ trách:** Mai Sơn Việt · **Sprint:** 1 · **Ước lượng:** 2 SP
**Phụ thuộc:** UI-03

### 1. User Story

- **Là người phát triển**, tôi muốn định nghĩa DTO và khung API thông báo, thống nhất phân trang, trạng thái đã đọc và đích điều hướng cho hai ứng dụng để triển khai và tích hợp đúng dữ liệu, quyền và contract của hệ thống.

### 2. Công việc

- Cùng BE-38/INT-11 lập field dictionary cho ID, nullable refId, Instant ISO-8601/timezone, text/type và isRead. Kiểm tra FE models để có adapter rõ, không đổi dữ liệu user sang locale như text hệ thống.
- Chốt route/default/bounds/PageResponse, ví dụ 0/1/nhiều trang và sort tie-breaker. Không thêm cursor pagination hoặc unread endpoint khi chưa có nhu cầu/contract.
- Chốt mark-read lặp, read-all count/cutoff khi thông báo đến đồng thời và lỗi owner/not-found; auth lấy từ backend, request không được chọn hộp thông báo của người khác.
- Chốt type/refId → navigation cùng producer KAFKA-12 và hai frontend, bao gồm type không biết, refId thiếu/đối tượng đã xóa. UI không tự thực thi HTML/link ngoài từ content notification.
- Hoàn thiện DTO/validation/OpenAPI skeleton tối thiểu trên source hiện có. Giữ phần chưa làm trả NOT_IMPLEMENTED theo error contract, không thêm handler trùng BE-38 hoặc giả isRead=true khi chưa lưu.
- Bàn giao example item/page/read/read-all/error và decision còn mở. Người phụ trách kiểm chứng serialize/deserialize khi được yêu cầu; không lấy fixture thể hiện UI làm bằng chứng ownership/persistence thật.

### 3. API

| API dự kiến theo đặc tả | Input / quyền | Response |
| --- | --- | --- |
| GET /api/notifications/my | Actor đã đăng nhập, page/size có bounds | PageResponse<NotificationResponse> chỉ của actor |
| PUT /api/notifications/{id}/read | id dương, owner lấy từ actor | NotificationReadResponse(id, true), hành vi lặp nhất quán |
| PUT /api/notifications/read-all | Actor, không userId tùy ý | NotificationReadAllResponse(updatedCount), số bản thực sự chuyển unread → read |

### 4. Tiêu chí hoàn thành

- A page=0,size=2 rồi page=1: Contract trả content tối đa 2/1, totalElements=3,totalPages=2, không tính B; sort có tie-breaker đã chốt
- User có 0 thông báo: content=[], totalElements=0, totalPages theo PageResponse đã chốt, không null/list toàn hệ thống
- Mark-read một record hai lần; reset fixture rồi read-all hai lần: Mark-read không nhân hiệu ứng; read-all updatedCount=2 rồi 0 nếu không có event mới
- Dùng id của B hoặc truyền userId=B: Error contract không lộ data B; không mô tả đổi owner qua body/query
- Page âm/size 0 hoặc 201, ID sai, type lạ/refId null: Validation hoặc fallback navigation rõ; không làm badge sai hoặc mở URL tùy ý
- Có notification mới khi read-all đang chạy: Contract nêu cutoff/count/read state cụ thể, không hứa đánh read cả bản chưa tồn tại
- Skeleton chưa implement được gọi theo cách hỗ trợ: Không trả 200 thành công giả; round-trip DTO khi người phụ trách chạy khớp FE contract
- Bàn giao contract, mã lỗi và kết quả tự kiểm thử kèm commit, môi trường, bằng chứng; ghi rõ lỗi hoặc phần còn bị chặn.

### 5. Điểm cần chốt

- Type/refId/link ở hai frontend; record bị xóa và type mới fallback thế nào?: KAFKA-12/INT-11 cùng owner UI; không tự dựng URL từ nội dung user
- Badge unread tổng ở đâu, update sau read-all và event mới: BE-38/INT-11; không dùng updatedCount như unreadCount
- Read-all cutoff/concurrency, ID wire format và nullable: BE-38 cùng UI; chặn expected count/adapter
