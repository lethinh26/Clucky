## BE-13 — Cấu hình OpenAPI và Swagger cho từng service, mô tả API và xác thực Bearer token theo môi trường

**Phụ trách:** Lê Phú Thịnh · **Sprint:** 1 · **Ước lượng:** 2 SP
**Phụ thuộc:** UI-03

### 1. User Story

- **Là người phát triển**, tôi muốn cấu hình OpenAPI và Swagger cho từng service, mô tả API và xác thực Bearer token theo môi trường để triển khai và tích hợp đúng dữ liệu, quyền và contract của hệ thống.

### 2. Công việc

- Liệt kê service có springdoc/config, endpoint đã có mapping và endpoint chỉ được nêu trong spec. Phân biệt rõ API thật với backlog; không tạo controller rỗng để làm docs trông đầy đủ.
- Đối chiếu OpenApiConfig/DTO/error schema từng service; dùng springdoc/annotation hiện có thay vì viết JSON OpenAPI thủ công trùng source.
- Đối chiếu bearer requirement của operation công khai/bảo vệ với API/RBAC và filter chain. Ghi ví dụ 400/401/403/404 theo BE-10, không trả một generic 200 cho mọi lỗi.
- Giữ config runtime ở Config Server. Kiểm tra flag và allowlist cùng bật/tắt; không permitAll toàn bộ API hoặc actuator để mở Swagger.
- Chốt URL docs nội bộ rồi cấu hình server URL phù hợp. Frontend vẫn gọi Gateway; URL docs nội bộ không phải lý do để frontend gọi business service trực tiếp.
- Người phụ trách tự mở docs/đọc JSON khi được phép và ghi evidence theo contract; không gọi mutation nghiệp vụ thật qua Try it out khi chỉ nghiệm thu docs.

### 3. Contract và đầu ra

- `/v3/api-docs` là JSON OpenAPI, `/swagger-ui.html` là entry UI theo tài liệu API; các asset UI cần được phục vụ khi bật. Chỉ là đường dẫn yêu cầu kiểm tra, chưa xác nhận URL môi trường đã hoạt động.
- Tên service/version rõ ràng; bearerAuth có scheme bearer và format JWT. Ví dụ dùng placeholder, không nhúng token, email thật, mật khẩu hoặc key.
- Schema ApiError có timestamp/status/error/code/message/path; PageResponse và DTO phản ánh JSON thật, không lộ JPA entity/hash/token internals.
- Phân trang page zero-based, size/sort và validation phải mô tả đúng endpoint đã có. Không thêm query parameter tưởng tượng cho endpoint chưa implement.
- Global bearerAuth hiện có phải được override đúng cho operation public khi triển khai controller: route công khai không bị tài liệu ghi là bắt buộc token; route bảo vệ không bị bỏ requirement.
- Docs chỉ mô tả giới hạn quyền, không thực thi RBAC. Try it out vẫn phải chịu security của API; docsEnabled không cấp quyền quản trị.

### 4. Tiêu chí hoàn thành

- Bật docs trong profile được duyệt, mở JSON và UI tại URL đã chốt: Title/version/service đúng; UI tải asset và JSON, không chỉ trả trang HTML trắng
- Đối chiếu một endpoint có thật với request/response DTO: Field/kiểu/required/page/error khớp code; không lộ password_hash/token_hash/JPA internals
- Xem operation public và operation bảo vệ: Public không bị khai báo bearer bắt buộc sai; protected có scheme/requirement đúng, Try it out không bypass quyền
- Tắt API_DOCS_ENABLED, truy cập JSON/UI/assets qua các đường công bố: Không nhận tài liệu/UI ngoài ý muốn; ghi rõ status thật, không đoán mọi đường đều phải cùng 404
- Đối chiếu spec với controller template chưa có mapping: Đánh dấu endpoint chưa triển khai trong bàn giao, không tuyên bố API hoạt động vì có tên trong tài liệu
- Kiểm tra example/server URL/security cấu hình: Không có credential/token/dữ liệu cá nhân thật; URL đúng môi trường, frontend entry point vẫn Gateway
- Bàn giao contract, mã lỗi và kết quả tự kiểm thử kèm commit, môi trường, bằng chứng; ghi rõ lỗi hoặc phần còn bị chặn.

### 5. Điểm cần chốt

- Docs qua Gateway hay truy cập từng service nội bộ?: Lê Phú Thịnh phối hợp UI-03/owner Gateway chốt host/path/routing/security. Chặn URL tích hợp cuối, không chặn schema/config cục bộ
- Môi trường nào được bật docs?: Owner deploy chốt API_DOCS_ENABLED và audience; giữ default false, không tự bật production
- Operation nào mới chỉ có spec?: Owner controller/domain xác nhận; BE-49 nhận nền tài liệu, không coi thiếu operation chưa code là task config phải triển khai nghiệp vụ
