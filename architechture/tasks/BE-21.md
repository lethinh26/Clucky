## 3. Contract cần triển khai

| Route theo API | Quyền / dữ liệu | Ranh giới |
|---|---|---|
| POST/PUT/DELETE /api/stores | ADMIN; name/address/phone/openTime/closeTime/status/deliveryArea | PUT/DELETE cần chốt vị trí resource ID vì đặc tả rút gọn chưa ghi /{id} |
| PUT /api/stores/{id}/operation | MANAGER quán mình hoặc ADMIN | Request allowlist vận hành: giờ/trạng thái/khu vực theo policy; không mở toàn bộ CRUD store cho Manager |
| POST/PUT/DELETE /api/catalog/categories | ADMIN; name/imageUrl/sortOrder/isActive | Xóa category có product cần policy tham chiếu |
| POST/PUT/DELETE /api/catalog/products | ADMIN; categoryId/name/description/basePrice và options/toppings | Chốt nested request hay route con; spec hiện không định nghĩa endpoint toppings riêng |
| POST/PUT/DELETE /api/catalog/combos | ADMIN; name/description/comboPrice/startAt/endAt/isActive/items | Mỗi item có productId/quantity/optionId; option phải thuộc đúng product |

Response dùng DTO đang có và cấu trúc detail đã chốt với BE-20. Request DTO phải riêng với entity: không nhận id/createdAt/actor cập nhật để ghi đè. Tiền BigDecimal đúng precision/scale SQL; basePrice không âm; validate độ dài/required, ID dương, số lượng item dương và thời gian hợp lệ theo contract.

Image URL/publicId chỉ nhận từ luồng media được duyệt; không kéo upload vào CRUD hoặc cho input tùy ý ghi đè metadata tin cậy. Không tự thêm lookup/download URL ảnh từ server.

## 4. Thứ tự thực hiện

1. Chốt request/response/status, ID route và update con là replace hay patch. Ghi ví dụ tạo product kèm option/topping và combo kèm item để INT-15 dùng cùng contract.
2. Làm stores/categories trước products, rồi combos. Mọi mutation kiểm tra role trước ghi; operation kiểm tra store của resource so với actor, không tin storeId body.
3. Validate toàn bộ category/product/option được tham chiếu trong schema Catalog. Combo có item sai phải thất bại cả thao tác; không lưu header rồi bỏ sót item lỗi.
4. Product/options/toppings và combo/items cập nhật trong transaction phù hợp. Kiểm tra option ID trong request thực sự thuộc product đang sửa; không dùng ID con để chuyển trái phép dữ liệu từ món khác.
5. Áp chính sách xóa/ẩn đã duyệt, xử lý FK/conflict rõ ràng; không cascade xóa dữ liệu ngoài phạm vi hoặc SQL vào Order. Không tự đổi DELETE thành hard-delete toàn cây.
6. Map response sau lưu, đọc lại qua BE-20 để xác nhận public contract. Phối hợp BE-54 invalidation, không tự xây cache mới tại đây.
7. Thay đổi quản trị cần đầu ra audit theo RBAC/INT-48, lọc secret trước lưu/phát; ghi rõ phần audit chưa nối nếu còn thiếu, không chỉ dựa vào log UI.
