## 1. Làm xong task này thì dùng được gì?

## 3. API/result/trust contract

| API / điểm giao | Yêu cầu |
|---|---|
| POST /api/catalog/products/{id}/image | ADM, resource tồn tại, multipart file; không upload orphan chỉ vì ID không tồn tại |
| POST /api/catalog/combos/{id}/image | Tương tự product, dùng scope/folder combo đúng |
| Adapter result | secureUrl HTTPS hợp lệ và publicId provider trả đúng context; không nhận client publicId làm bằng chứng ownership |
| Response endpoint | Source trả resource DTO, API mô tả secureUrl/publicId; BE-71/72/INT-72 phải chốt wire response/mapping, không nói đã trùng tên trường |
| Delete/cleanup | Nội bộ sau metadata decision theo API docs; không cho xóa asset bất kỳ bằng URL/publicId client gửi |

5MiB/jpeg/png/webp là giới hạn trong source hiện tại, chưa tự là policy sản phẩm đã duyệt. BE-71 xác nhận allowed type/max bytes/content sniffing; không chỉ tin Content-Type hoặc đuôi file. Không fetch remote URL tùy client để upload thay file, không gửi API_SECRET/browser.

## 4. Thứ tự hoàn thiện cụ thể

1. Rà source có sẵn với BE-68/71, xác định binding authoritative và backend multipart flow hiện tại. Không triển khai signed flow thứ hai trừ khi owner chọn; thống nhất request/response field trước tích hợp.
2. Kiểm tra auth/resource trước provider call; validate actual file content/size/mime và giới hạn decode theo BE-71. Từ chối file giả ảnh, ID sai hoặc role thiếu bằng error contract chuẩn.
3. Harden adapter hiện có: timeout/network/provider exception an toàn, validate secure_url/public_id/type trước trả. Không lưu null metadata hoặc trả success URL giả khi disabled/response provider thiếu; không log exception raw có secret.
4. Upload ảnh mới với identity không ghi đè ảnh cũ đang dùng trước DB commit; rà overwrite/resource/folder semantics theo provider contract. Chốt retry sau timeout chưa rõ provider đã tạo asset hay chưa, tránh orphan không kiểm soát.
5. Lưu metadata transaction và version/concurrency policy: hai replace gần nhau phải giữ ảnh cuối hợp lệ, cleanup không xóa asset đang được record tham chiếu. Đừng giữ transaction DB/network kéo dài ngoài nhu cầu nếu có cách tách an toàn được duyệt.
6. Nếu upload thành công nhưng DB rollback, giữ ảnh cũ và ghi nhận orphan mới theo BE-74. Sau commit ảnh mới mới enqueue cleanup cũ; afterCommit destroy hiện tại cần nối durable recovery, không báo cleanup thành công khi chỉ log lỗi.
7. Chốt/delete boundary cùng BE-74: verify ownership/reference, publicId có slash không bị xử lý sai route, distinguish provider not-found/failure/disabled. HTTP204 không được che failure hoặc cho xóa asset đang dùng; không tự broaden ADMIN thành quyền xóa mọi asset.
8. Nối readback/product/combo/menu cache invalidation sau commit theo BE-54; response và dữ liệu DB dùng metadata mới. Bàn giao BE-72/INT-72 lỗi/loading/replace semantics, evidence thật INT-01 khi được phép chạy, không giả upload đã test.
